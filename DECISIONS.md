# pragma.component-rhi decisions

ADR log. A decision changes only through a new entry with a reason (the old one is not deleted, it is marked "superseded by #N").

| # | Decision | Choice | Why | Date |
|---|---------|-------|--------|------|
| 1 | Component boundaries | A Render Hardware Interface: instance, adapters, devices, queues, buffers, textures, samplers, shader modules, bind groups, pipelines, command recording and submission, surfaces and frames in flight. **No** windowing or input, no renderer (materials, meshes, scenes, lighting), no asset loading, no ECS integration, no game loop | pragma.core DECISIONS #1 leaves rendering to layers above the core; a renderer is a decision of a specific engine and must stay replaceable, while the hardware interface under it is shared | 2026-11-09 |
| 2 | Relation to pragma.core | Depends on the `pragma_core` facade (1.x from crates.io) with `default-features = false`, enabling only what it uses (`jobs`, `graph`, later `async`). No own threads: command recording runs as tasks of the pragma.core frame graph on the engine's `ThreadPool`, uploads and pipeline compilation as pragma.core async tasks | One pool per process (pragma.core #1); the frame graph already orders tasks and validates resource conflicts at build time, which is what parallel command encoding needs. The facade, not individual crates, per pragma.core's versioning policy | 2026-11-09 |
| 3 | Platforms and toolchain | The same as pragma.core: Windows and Linux (x86_64) in CI; edition 2024, MSRV 1.88, pinned 1.99.0. GPU APIs: Vulkan (Windows, Linux) and D3D12 (Windows) through the backend of #8; the headless null backend everywhere | The component ships together with the core and pragma.component-ecs; diverging toolchains would only add friction. CI runners have no GPU, so a backend without one is part of the platform list (roadmap M1) | 2026-11-09 |
| 4 | Workspace and versions | A Cargo workspace (`crates/*`), one crate `pragma_rhi` for now; all crates share one version (lockstep), internal dependencies `=X.Y.Z`. Starting at 0.0.1, `publish = false` until the API review | The same policy as pragma.core #33/#42 and pragma.component-ecs #4; splitting into crates happens when a layer boundary appears (for example a backend crate), not in advance | 2026-11-09 |
| 5 | Dependency purity | Pure Rust only, checked by `cargo deny` and `tools/audit_workspace.py` (copied from pragma.component-ecs). `generator` (via `pragma_sync` → `loom`, only under `cfg(loom)`) is accepted in `[purity.accepted]`. Prebuilt import libraries (`windows-targets`) and runtime loading of system GPU drivers (`vulkan-1.dll`, `libvulkan.so`, `d3d12.dll`) are not compiled C/C++; whatever the backend pulls in is audited when it is added (M1) and every exception gets its own entry | The same rule as pragma.core #4; a GPU driver is part of the OS, not of the dependency tree, but anything built from C/C++ source is not | 2026-11-09 |
| 6 | `unsafe` policy | `#![forbid(unsafe_code)]` in every crate; `unsafe_allowed` stays empty. The FFI `unsafe` of the GPU APIs lives inside the backend (#8), not in this repository. A native backend of our own would need a separate decision, a dedicated crate, a budget in `layers.toml`, `// SAFETY:` on every block and Miri where it applies | Confines the risk, as pragma.core #6/#27 and pragma.component-ecs #6 did; with wgpu as the backend nothing here needs `unsafe` | 2026-11-09 |
| 7 | Documentation language | English everywhere: README, `docs/`, this log, rustdoc, comments | The same as pragma.core #43 and pragma.component-ecs #7 | 2026-11-09 |
| 8 | GPU backend | `wgpu` (pure Rust: Vulkan through `ash`, D3D12 through `windows`, shaders through `naga`) as the only hardware backend, **hidden** behind `pragma_rhi`'s own types: no `wgpu` type in the public API. A null backend in `pragma_rhi` for headless, deterministic tests. Golden-image tests run on software adapters (WARP on Windows, lavapipe on Linux). Own native backends (`ash` / `windows` directly) are out of scope before 1.0 | wgpu keeps all FFI `unsafe` out of this repository (#6) and covers both platforms (#3). wgpu ships a major release every few months: keeping its types private means a wgpu upgrade is a minor release of `pragma_rhi`, as the puffin upgrade is for pragma_core (pragma.core #42), not a breaking one. Own backends would be the largest and riskiest part of the component and are not needed to reach a stable API | 2026-11-09 |
| 9 | Resource handles | **Generational ids** (device id + slot index + generation, 12 bytes, `Copy`) into per-device tables, one table per resource kind. Destruction is explicit (`Device::destroy_*`); a destroyed handle returns `RhiError::StaleHandle`, another device's handle `RhiError::ForeignHandle`. A slot whose generation would wrap is retired, never reused. Device ids are unique per process. A texture with live views cannot be destroyed (`RhiError::ResourceInUse`) | The same model as `Entity` in pragma_ecs: cheap to store in components, and stale use is a typed error instead of a use-after-free or a silent alias. Reference-counted handles would make lifetimes implicit, and `Drop` cannot report an error; explicit destruction is also what deferred destruction (M4) builds on | 2026-11-09 |
| 10 | Backend seam | An internal **enum** `DeviceBackend { Wgpu, Null }` (and `Obj<W> { Wgpu(W), Null }` for resource objects), not a trait object. The front end validates every descriptor; the backends only create objects | There are exactly two backends (#8); an enum gives exhaustive matching (a forgotten backend is a compile error), no dynamic dispatch and no object-safety limits on generic methods. A third backend would be a new variant and a new decision | 2026-11-09 |
| 11 | wgpu dependency tree | `wgpu` 30 with `default-features = false` and only `std`, `parking_lot`, `vulkan`, `dx12`, `wgsl`: no GLES (EGL, ANGLE), Metal or WebGPU. `pollster` blocks on wgpu's adapter, device and error-scope futures (no async runtime). Audit: `cargo deny` passes with no new exception; `tools/audit_workspace.py` finds no C/C++ build; `renderdoc-sys`, `windows-sys` and the `ash` loader are bindings to system libraries loaded at run time (#5). wgpu's default uncaptured-error handler (which panics) is replaced; every creation runs in out-of-memory and validation error scopes | Keeps the tree to the two supported APIs (#3) and pure Rust (#5), and turns every wgpu failure into an `RhiError` (architecture §5) | 2026-11-09 |
| 12 | Descriptor style | Input structs (`*Descriptor`, `Limits`, `NullConfig`, `InstanceDescriptor`) are plain structs with public fields and `Default`, used with `..Default::default()`, as in wgpu. Output structs (`*Info`, `AdapterInfo`) and `RhiError` variants are `#[non_exhaustive]`; errors are matched with `..` | `#[non_exhaustive]` forbids struct-update syntax outside the crate, which would make descriptors unusable; a new input field before 1.0 is a minor (0.x) release. Outputs can grow without breaking callers | 2026-11-09 |
| 13 | Shader front end | `pragma_rhi` parses and validates every shader with `naga` (the version wgpu is built on, `wgsl-in` + `spv-in`) **before** any backend, reflects each entry point (resources used, `@location` inputs and outputs, workgroup size) and hands the module to wgpu as naga IR (`wgpu` feature `naga-ir` instead of `wgsl`). SPIR-V is translated and validated like WGSL, not passed through: wgpu's raw SPIR-V path is `unsafe` (#6). WGSL errors carry line and column (`RhiError::Shader`). Pipeline creation checks the reflection against the pipeline layout, vertex buffers, color targets and workgroup limits (`RhiError::ShaderInterface`) | The null backend must reject exactly the shaders wgpu rejects, or tests on CI (no GPU) would pass shaders a GPU refuses; validating once in our front end gives that, plus errors with a source location and a shader interface check that wgpu reports only as an opaque validation string. One naga version for both parsing and wgpu keeps the IR compatible; a wgpu upgrade moves both together | 2026-11-09 |
| 14 | Pipelines: dependencies, cache, async compilation | Bind groups pin their layout and every bound buffer, sampler and view; pipeline layouts pin their bind group layouts; pipelines pin their pipeline layout (`RhiError::ResourceInUse`, counted per device). Shader modules are not pinned: a pipeline keeps its compiled code. Every device has a **pipeline cache** keyed by everything a compiled pipeline depends on (layout and module serials never reused on the device, entry points, vertex layouts, fixed-function state; not the label); entries are dropped with their module or layout; every creation still returns its own handle. `compile_*_pipeline(desc, &Executor)` validates synchronously and compiles on the pragma.core executor's **blocking pool**; the caller installs the result with `poll_*` (non-blocking, once per frame) or `wait_*` (outside pool work). The device is never touched from another thread; a layout destroyed during compilation makes the result `StaleHandle` | The same explicit-lifetime model as #9 extended to the objects that reference others, so no destroy can leave a dangling reference for command recording (M3). A cache keyed by the validated descriptor avoids recompiling identical pipelines, which engines request repeatedly per material. Driver compilation can take milliseconds to seconds; the blocking pool is pragma.core's place for such work (pragma.core async), and polling keeps the frame thread in control of when results appear | 2026-11-09 |
| 15 | Command recording and submission | A `CommandEncoder` records **plain data**: commands that name resources by handle, with no device access, no lock and no fallible call; passes are scoped borrows of the encoder (`RenderPass`, `ComputePass`). `Device::submit` validates every command of every buffer against the live tables (handles, usages, alignments and ranges, attachments, pipeline and bind group compatibility, dynamic offsets, draw ranges, late `min_binding_size`, WebGPU usage scopes) and resolves handles before the backend sees anything; a broken rule rejects the whole submission with `RhiError::InvalidCommand` (command buffer label + command + reason). Recording on the frame graph goes through `CommandGraph`: each recording task fills one encoder labeled with the task name, declares access by type like any pragma.core task, and the buffers come back in the graph's topological order; a failed recording keeps its typed `RhiError`, the first in that order wins. Resources referenced by recorded but unsubmitted commands are not pinned: a destroyed one is `StaleHandle` at submission. wgpu encodes the validated commands on the submitting thread | Parallel recording needs encoders that are `Send`, independent of the single-owner device (#14) and cheap; plain data gives that and keeps the device lock-free. Validating at submission in our front end, instead of letting wgpu reject commands, makes the null backend reject exactly what wgpu rejects (as #13 does for shaders) and turns wgpu's opaque validation strings into typed errors that name the task. Rejecting a submission as a whole means no half-executed frame. Topological order is deterministic on any number of workers, which golden images and replays need. Encoding wgpu commands per submission is single-threaded; if M5's benchmarks show it matters, batches can be encoded in parallel (wgpu encoders are `Send`) without changing the API | 2026-11-09 |
| 16 | Null backend memory | The null backend keeps the bytes of buffers and textures, allocated lazily on first write (reads of unwritten memory are zero), one sample per texel, laid out linearly per layer and mip. It executes queue writes, buffer clears, every copy, attachment clears (with WebGPU's conversion: unorm round-to-nearest, sRGB encoding of color channels, f16 round-to-nearest-even), resolves (a copy: every null sample holds the same value) and `StoreOp::Discard` (zeros). Draws and dispatches are validated and have no effect. Readback (`read_buffer`, `read_texture`) is blocking before frames in flight (M4) | Readback tests and the vertical slice must run on CI runners without a GPU; transfers are fully specified, so the null backend can reproduce them exactly — and does: the M3 tests compare the bytes with Vulkan, D3D12 and WARP. Shaders would need an interpreter, which is out of scope; deterministic no-op draws keep the null backend's output stable. Lazy allocation keeps large null resources (budgets up to GiBs in tests) free until used | 2026-11-09 |
| 17 | Frames in flight and deferred destruction | Every submission gets a `SubmissionIndex` (1, 2, …); the device learns completion only when it polls (`poll`, `wait`, `begin_frame`, blocking reads), from wgpu's `on_submitted_work_done` callbacks. A frame is `begin_frame` … `end_frame`; its fence is the last submission in it; `begin_frame` blocks until at most `frames_in_flight - 1` (1..=8, default 2) earlier frames are in flight and returns the slot of `PerFrame` resources. `destroy_buffer` / `destroy_texture` stale the handle at once and keep the backend object until every submission made so far has retired (a conservative fence, no per-resource tracking). The null backend runs commands at once but reports a submission complete `NullConfig::latency` submissions later or when waited for | A bounded CPU lead is what keeps frame latency and per-frame memory bounded; blocking in `begin_frame` is the standard place for it. Polling instead of callbacks into engine code keeps the device single-owner (#14). Tagging garbage with the last submission is exact enough at frame granularity and costs nothing per command; per-resource last-use tracking can come if M5's benchmarks show held memory matters. A latency knob makes every pacing and destruction rule testable on CI without a GPU | 2026-11-10 |
| 18 | Surfaces | `Instance::create_surface` takes anything with `raw-window-handle` 0.6 window and display handles (`Send + Sync + 'static`, kept alive by the surface) through wgpu's safe path; the crate opens no windows. A `Surface` is a value, not a handle: configured for one device at a time. The device validates every configuration against the surface's capabilities and its limits (wgpu panics on a bad one) and resolves `Auto` modes. An acquired frame is a texture in the device's table (plus a default view), so commands, validation and copies need nothing new; `present` / `discard_frame` stale both; `destroy_texture` refuses a swapchain texture; a frame with extra views cannot be presented. Outdated, lost, timeout and occluded are `SurfaceError`s from `acquire_frame`. A null surface plays a window for tests | `raw-window-handle` is the ecosystem's neutral window interface (winit, SDL, native), so windowing stays out of scope (#1). Making the swapchain image an ordinary texture reuses M3's whole validation (#15) instead of a parallel path. Validating up front turns every wgpu panic of `configure` into a typed error | 2026-11-10 |
| 19 | Uploads and readback | A staging belt per device: `MAP_WRITE | COPY_SRC` chunks (1 MiB by default, larger uploads get their own) mapped on the CPU, bounded by `UploadConfig::capacity` (64 MiB). `upload_buffer` / `upload_texture` validate the copy, write the bytes into a chunk at once (texture rows repacked to the 256-byte alignment, so any source stride works) and record a copy that runs first in the next submission, after queue writes; chunks are unmapped when submitted and mapped again when that submission retires. A full belt reuses retired chunks, drops idle ones, then blocks on the oldest chunk in flight. A rejected submission keeps its uploads; destroying a buffer or texture flushes pending uploads first. `upload_async` runs the byte producer on pragma.core's blocking pool and uploads when polled. `read_*_async` copy into a `MAP_READ` buffer as their own submission; `poll_readback` maps it after that submission retires; a dropped readback's staging is freed on the next poll. The chunks and staging buffers are device buffers and count in `live` | Per-frame uploads need bounded, recycled staging memory, which `write_buffer` does not give; copying the caller's bytes at once means the caller's slice is free immediately and the upload cannot observe later changes. Using ordinary buffers and recorded copies keeps the null backend and validation identical to the GPU path (the M4 tests compare the bytes with Vulkan, D3D12 and WARP). Producing bytes off-thread and installing them on the frame thread is the same pattern as pipeline compilation (#14) | 2026-11-10 |
| 20 | Golden images (M5) | Example `rhi_golden` renders seven 64 × 64 scenes (interpolated colors, alpha blending, depth test with back-face culling, a 4x MSAA resolve, a sampled checkerboard on an indexed, instanced quad with a viewport and a scissor, an sRGB target, a compute shader writing a storage texture and integer hashes into a storage buffer) and hashes each readback (FNV-1a 64). **Hashes per adapter** are committed in `examples/rhi_golden/golden.txt` (`<adapter> <scene> <hash>`): `warp` (D3D12, `DeviceType::Cpu`) and `lavapipe` (Vulkan, `Cpu`, name contains `llvmpipe`). CI requires the adapter (`--adapter warp` on Windows, `--adapter lavapipe` on Linux after installing `mesa-vulkan-drivers`): an absent adapter, a missing entry or a different hash fails; `--dump DIR` then writes every scene as PPM plus the `golden.txt` the run would bless, uploaded as an artifact; `--bless` rewrites one adapter's lines. Every scene runs twice on fresh resources and must give the same bytes. Hardware adapters run the scenes only for information | The user's choice among three options (hashes per adapter / one reference image with a tolerance / only WARP == lavapipe). Software rasterizers legitimately differ in the last bit (WARP and an NVIDIA GTX 650 already differ on 6 of 7 scenes), so a cross-adapter equality could only cover integer-exact scenes; exact hashes per adapter catch any behaviour change with no tolerance to tune and no image files in the repository. A WARP or Mesa update on the runner images that changes rasterization shows up as a reviewed `golden.txt` diff. The lavapipe hashes come from the first CI run (no lavapipe locally) | 2026-11-10 |
| 21 | Fuzzing (M5) | **cargo-fuzz** in a separate `fuzz/` workspace (nightly; `libfuzzer-sys` is C++), as pragma.core #20 and pragma.component-ecs #30: not a member of the main workspace, so neither users' trees nor `cargo deny` / the audit see it. Three targets — `handles` (buffers, textures, views created, destroyed and queried with submissions, polls and frames on a null device with latency 2, against a model of handles, memory, deferred destruction and fences), `descriptors` (arbitrary buffer, texture, view and sampler descriptors against the buffer and sampler rules modeled exactly and the texture and view rules modeled as sufficient-to-reject; a failed creation changes nothing) and `transfers` (queue writes and submissions of copies and clears against a model of buffer contents; a broken submission changes nothing) — decode bytes into operations; the oracles live in `crates/pragma_rhi/tests/common/` and `tests/oracle.rs` runs them through proptest with the same decoders. CI: 60 s per target on Linux in every PR that touches code; nightly 10 min per target with the corpus in the Actions cache. On Windows the oracles run through proptest only: libFuzzer's sancov sections do not link with MSVC | The user's choice between cargo-fuzz and proptest only. Coverage-guided fuzzing reaches validation branches random generation rarely hits, and the dev-only workspace repeats a documented decision of both sibling repositories; one oracle per property turns a fuzz finding into a proptest input without translation. Each oracle was checked to fail on a deliberate mutation of its model | 2026-11-10 |
| 22 | Device-loss recovery (M5) | No API change; the recovery contract is now tested (`tests/device_loss.rs`): after `simulate_device_loss` with resources of every kind alive, a frame open, submissions, a deferred destruction, a readback, a pipeline compilation and an async upload in flight, an upload staged and a swapchain frame acquired, every entry point returns `RhiError::DeviceLost`, waits on blocking-pool work end with it, and dropping the lost device is clean. Recovery: a new device from the same adapter (old handles are `ForeignHandle` there), rebuilt resources give byte-identical results with latency 0 and 2, `configure_surface` on the new device takes the surface over even with the lost device's frame acquired, and the pool and executor serve the new device. Nightly toolchains warn about the depth of wgpu-core's `Send` proof; `pragma_rhi` sets `recursion_limit = 256` | Device loss is the failure an engine must survive without restarting; the behaviour existed since M1/M4 but only single calls were tested. The recursion limit keeps the crate compiling when that future-incompatibility warning becomes an error (rust-lang/rust#159228) | 2026-11-10 |
| 23 | Benchmarks (M5) | `criterion` 0.8 (the version of pragma.core and pragma.component-ecs) as a dev dependency; its `alloca` (C via `cc`) is accepted in `[purity.accepted]` like in both siblings (`deny.toml` excludes the dev graph). Three bench targets on the **null backend**, 1000 operations each: `resources` (buffer churn, texture + view churn, bind group churn), `recording` (1000 draws, 1000 copies, 1000 draws by 8 `CommandGraph` tasks on 4 workers) and `submission` (validating and executing 1000 draws, 1000 copies, a frame of 1000 draws). Each group also measures the reference `hashmap_churn` (1000 inserts and removes of a std `HashMap`). `[lib] bench = false`, so `cargo bench -p pragma_rhi -- <criterion flags>` works. Numbers in `docs/architecture.md` §6; the nightly workflow writes all medians into its summary | The null backend measures `pragma_rhi`'s own costs (tables, validation, recording) without driver noise, which is what a change to this crate can affect; GPU submission cost belongs to wgpu. A reference inside every bench target is what the gate needs to separate runner noise from a regression | 2026-11-10 |
| 24 | Bench gate (M5) | `tools/bench_gate.py`, adapted from pragma.component-ecs (#32, #43, #44 there): in PRs on Windows and Linux the PR base and head are built into separate target directories with aligned loops, every measurement runs in its own process (`MALLOC_ARENA_MAX=1` on Linux), 3 interleaved rounds, the best median counts. A measurement fails if `head/base` **and** its value normalized by the `hashmap_churn` shift exceed `1.1 +` its own process-to-process spread. A base without the benchmarks (this PR's) reports instead of gating. A `changes` job skips the gate, fuzzing and semver-checks on PRs touching only `*.md` / `docs/` | The user's choice (criterion with an A/B gate). The methodology and its fixes for shared-runner noise already exist in the siblings; a self-test of the same tree against itself gave every ratio within ± 2 % except one run of `encode_draws` (−17 %), which is why the spread term stays | 2026-11-10 |
| 25 | Semver checks and the version (M5) | `cargo semver-checks -p pragma_rhi --baseline-rev <PR base>` in PRs on Windows and Linux (named explicitly: `--workspace` skips `publish = false` crates). The workspace version becomes **0.5.0**, untagged: the owner tags and releases | The user's choice (main + 0.5.0), as pragma.component-ecs #33: comparing with `main` catches a breaking change in the PR that makes it, and the version follows the milestone | 2026-11-10 |
| 26 | Reference environment of the golden images (amends #20) | The hashes in `golden.txt` are those of the **CI runners**: WARP of `windows-latest` and lavapipe of `ubuntu-latest` (Mesa llvmpipe, LLVM 21, 256 bits), taken from the `golden-*` artifacts of the first M5 run. A local run on another Windows build may differ on a scene and is not a failure of the code: WARP on Windows 10 (where the WARP hashes were first blessed) differs from the runner's in `textured` by ±1 in 437 bilinear-filtered pixels; every other scene matches. Hashes are changed only from CI artifacts | The first CI run showed that WARP's filtering precision depends on the Windows build; the runners are the environment every PR is checked in, so their output is the reference, and a bless from a developer's machine would make CI fail. The lavapipe and WARP images agree visually on every scene | 2026-11-10 |
| 27 | API review for 1.0: extensibility (M6) | No renames, no removals: the 0.5.0 API stays. **`#[non_exhaustive]`** on every enum that will gain variants as GPUs and WebGPU grow — `RhiError` (and each of its struct variants), `SurfaceError`, `TextureFormat`, `VertexFormat`, `BindingType`, `BindingResource`, `BufferBindingType`, `SamplerBindingType`, `TextureSampleType`, `StorageTextureAccess`, `TextureViewDimension`, `TextureAspect`, `AddressMode`, `BlendFactor`, `PrimitiveTopology`, `LoadOp`, `PresentMode`, `CompositeAlphaMode`, `ShaderSource`, `ShaderStage`, `UploadTarget`, `ResourceKind`, `Backend`, `DeviceType` — and on the structs the crate fills in: `Limits`, `AdapterInfo`, every `*Info`, `SurfaceCapabilities`, `SurfaceFrame`, `UploadStats`, `PipelineCacheStats`, `SourceLocation`. `Limits` is also an input (`DeviceDescriptor::required_limits`, `NullConfig::limits`): outside the crate it is built from `Limits::default()` or `Adapter::limits()` and changed field by field. **Exhaustive**, because the set is complete: `Face`, `FrontFace`, `IndexFormat`, `FilterMode`, `VertexStepMode`, `TextureDimension`, `StencilOperation`, `CompareFunction`, `BlendOperation`, `StoreOp`. **Descriptors** (`*Descriptor`, `*State`, `*Entry`, `*Attachment`, `TexelCopy*`, `UploadConfig`, `NullConfig`, `SurfaceConfiguration`) stay plain structs with public fields and `Default` (#12): a new field there waits for 2.0 or comes as a new descriptor or method. Bit flags (`BufferUsages`, `TextureUsages`, `ShaderStages`, `ColorWrites`, `Backends`) gain bits without a break. wgpu's version is not part of the API (#8) | The user's choice among three options (growing enums and output structs / errors only, as pragma.component-ecs #36 / everything including descriptors). An RHI follows a moving target: new texture and vertex formats, binding types, present modes and error cases come with GPU and WebGPU features, and without the attribute each one would need a 2.0. Output structs are only read by users, so the attribute costs nothing there. Making descriptors non-exhaustive would forbid struct literals with `..Default::default()` outside the crate, the style #12 chose and every example uses, and would need a builder for each | 2026-11-10 |
| 28 | `pub use pragma_core` (M6) | The crate root re-exports the `pragma_core` it is built with; the docs and examples name `ThreadPool`, `Resources` and `Executor` through it. `pragma_core` types in the API (`ThreadPool`, `Resources`, `TaskConfig`, `TaskContext`, `Executor`, `GraphError`, `AsyncError`) tie a `pragma_core` 2.0 to a `pragma_rhi` 2.0 | The user's choice, as pragma.component-ecs #36: users get exactly the version `CommandGraph::record`, `compile_*_pipeline` and `upload_async` take, without adding the dependency by hand | 2026-11-10 |
| 29 | Embedding documentation and rustdoc (M6) | As pragma.core #46 and pragma.component-ecs #38: no separate guide. The crate docs have **"Semver guarantees"** (#27, #28) and **"Integrating into an engine"** (one instance and device, the single-owner device and parallel recording, one pool and executor, the frame sequence, explicit lifetimes, errors to react to — surface errors, device loss, invalid commands —, determinism and tests on the null backend, shutdown order) with a compiled renderer skeleton that resizes and recovers from a device loss on the null backend. An example on every public type (the ten handle types share one, generated by their macro), on the free constants and on the main methods; getters and associated constants are covered by their type's example. 155 doctests, run in CI | Rustdoc examples are compiled and run on every PR, a Markdown guide is not, and the crate page is the first page a docs.rs reader opens. Every example runs on the null backend, so CI needs no GPU for them | 2026-11-10 |
