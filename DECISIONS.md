# pragma.component-rhi decisions

ADR log. A decision changes only through a new entry with a reason (the old one is not deleted, it is marked "superseded by #N").

| # | Decision | Choice | Why | Date |
|---|---------|-------|--------|------|
| 1 | Component boundaries | A Render Hardware Interface: instance, adapters, devices, queues, buffers, textures, samplers, shader modules, bind groups, pipelines, command recording and submission, surfaces and frames in flight. **No** windowing or input, no renderer (materials, meshes, scenes, lighting), no asset loading, no ECS integration, no game loop | pragma.core DECISIONS #1 leaves rendering to layers above the core; a renderer is a decision of a specific engine and must stay replaceable, while the hardware interface under it is shared | 2026-11-09 |
| 2 | Relation to pragma.core | Depends on the `pragma_core` facade (1.x from crates.io) with `default-features = false`, enabling only what it uses (`jobs`, `graph`, later `async`). No own threads: command recording runs as tasks of the pragma.core frame graph on the engine's `ThreadPool`, uploads and pipeline compilation as pragma.core async tasks | One pool per process (pragma.core #1); the frame graph already orders tasks and validates resource conflicts at build time, which is what parallel command encoding needs. The facade, not individual crates, per pragma.core's versioning policy | 2026-11-09 |
| 3 | Platforms and toolchain | The same as pragma.core: Windows and Linux (x86_64) in CI; edition 2024, MSRV 1.88, pinned 1.99.0. GPU APIs: Vulkan (Windows, Linux) and D3D12 (Windows) through the backend of #8; the headless null backend everywhere | The component ships together with the core and pragma.component-ecs; diverging toolchains would only add friction. CI runners have no GPU, so a backend without one is part of the platform list (roadmap M1) | 2026-11-09 |
| 4 | Workspace and versions | A Cargo workspace (`crates/*`), one crate `pragma_rhi` for now; all crates share one version (lockstep), internal dependencies `=X.Y.Z`. Starting at 0.0.1, `publish = false` until the API review | The same policy as pragma.core #33/#42 and pragma.component-ecs #4; splitting into crates happens when a layer boundary appears (for example a backend crate), not in advance | 2026-11-09 |
| 5 | Dependency purity | Pure Rust only, checked by `cargo deny` and `tools/audit_workspace.py` (copied from pragma.component-ecs). `generator` (via `pragma_sync` → `loom`, only under `cfg(loom)`) is accepted in `[purity.accepted]`. Prebuilt import libraries (`windows-targets`) and runtime loading of system GPU drivers (`vulkan-1.dll`, `libvulkan.so`, `d3d12.dll`) are not compiled C/C++; whatever the backend pulls in is audited when it is added (M1) and every exception gets its own entry | The same rule as pragma.core #4; a GPU driver is part of the OS, not of the dependency tree, but anything built from C/C++ source is not | 2026-11-09 |
| 6 | `unsafe` policy | `#![forbid(unsafe_code)]` in every crate; `unsafe_allowed` stays empty. The FFI `unsafe` of the GPU APIs lives inside the backend (#8), not in this repository. A native backend of our own would need a separate decision, a dedicated crate, a budget in `layers.toml`, `// SAFETY:` on every block and Miri where it applies | Confines the risk, as pragma.core #6/#27 and pragma.component-ecs #6 did; with wgpu as the backend nothing here needs `unsafe` | 2026-11-09 |
| 7 | Documentation language | English everywhere: README, `docs/`, this log, rustdoc, comments | The same as pragma.core #43 and pragma.component-ecs #7 | 2026-11-09 |
| 8 | GPU backend | `wgpu` (pure Rust: Vulkan through `ash`, D3D12 through `windows`, shaders through `naga`) as the only hardware backend, **hidden** behind `pragma_rhi`'s own types: no `wgpu` type in the public API. A null backend in `pragma_rhi` for headless, deterministic tests. Golden-image tests run on software adapters (WARP on Windows, lavapipe on Linux). Own native backends (`ash` / `windows` directly) are out of scope before 1.0 | wgpu keeps all FFI `unsafe` out of this repository (#6) and covers both platforms (#3). wgpu ships a major release every few months: keeping its types private means a wgpu upgrade is a minor release of `pragma_rhi`, as the puffin upgrade is for pragma_core (pragma.core #42), not a breaking one. Own backends would be the largest and riskiest part of the component and are not needed to reach a stable API | 2026-11-09 |
| 9 | Resource handles | **Generational ids** (device id + slot index + generation, 12 bytes, `Copy`) into per-device tables, one table per resource kind. Destruction is explicit (`Device::destroy_*`); a destroyed handle returns `RhiError::StaleHandle`, another device's handle `RhiError::ForeignHandle`. A slot whose generation would wrap is retired, never reused. Device ids are unique per process. A texture with live views cannot be destroyed (`RhiError::ResourceInUse`) | The same model as `Entity` in pragma_ecs: cheap to store in components, and stale use is a typed error instead of a use-after-free or a silent alias. Reference-counted handles would make lifetimes implicit, and `Drop` cannot report an error; explicit destruction is also what deferred destruction (M4) builds on | 2026-11-09 |
| 10 | Backend seam | An internal **enum** `DeviceBackend { Wgpu, Null }` (and `Obj<W> { Wgpu(W), Null }` for resource objects), not a trait object. The front end validates every descriptor; the backends only create objects | There are exactly two backends (#8); an enum gives exhaustive matching (a forgotten backend is a compile error), no dynamic dispatch and no object-safety limits on generic methods. A third backend would be a new variant and a new decision | 2026-11-09 |
| 11 | wgpu dependency tree | `wgpu` 30 with `default-features = false` and only `std`, `parking_lot`, `vulkan`, `dx12`, `wgsl`: no GLES (EGL, ANGLE), Metal or WebGPU. `pollster` blocks on wgpu's adapter, device and error-scope futures (no async runtime). Audit: `cargo deny` passes with no new exception; `tools/audit_workspace.py` finds no C/C++ build; `renderdoc-sys`, `windows-sys` and the `ash` loader are bindings to system libraries loaded at run time (#5). wgpu's default uncaptured-error handler (which panics) is replaced; every creation runs in out-of-memory and validation error scopes | Keeps the tree to the two supported APIs (#3) and pure Rust (#5), and turns every wgpu failure into an `RhiError` (architecture §5) | 2026-11-09 |
| 12 | Descriptor style | Input structs (`*Descriptor`, `Limits`, `NullConfig`, `InstanceDescriptor`) are plain structs with public fields and `Default`, used with `..Default::default()`, as in wgpu. Output structs (`*Info`, `AdapterInfo`) and `RhiError` variants are `#[non_exhaustive]`; errors are matched with `..` | `#[non_exhaustive]` forbids struct-update syntax outside the crate, which would make descriptors unusable; a new input field before 1.0 is a minor (0.x) release. Outputs can grow without breaking callers | 2026-11-09 |
| 13 | Shader front end | `pragma_rhi` parses and validates every shader with `naga` (the version wgpu is built on, `wgsl-in` + `spv-in`) **before** any backend, reflects each entry point (resources used, `@location` inputs and outputs, workgroup size) and hands the module to wgpu as naga IR (`wgpu` feature `naga-ir` instead of `wgsl`). SPIR-V is translated and validated like WGSL, not passed through: wgpu's raw SPIR-V path is `unsafe` (#6). WGSL errors carry line and column (`RhiError::Shader`). Pipeline creation checks the reflection against the pipeline layout, vertex buffers, color targets and workgroup limits (`RhiError::ShaderInterface`) | The null backend must reject exactly the shaders wgpu rejects, or tests on CI (no GPU) would pass shaders a GPU refuses; validating once in our front end gives that, plus errors with a source location and a shader interface check that wgpu reports only as an opaque validation string. One naga version for both parsing and wgpu keeps the IR compatible; a wgpu upgrade moves both together | 2026-11-09 |
| 14 | Pipelines: dependencies, cache, async compilation | Bind groups pin their layout and every bound buffer, sampler and view; pipeline layouts pin their bind group layouts; pipelines pin their pipeline layout (`RhiError::ResourceInUse`, counted per device). Shader modules are not pinned: a pipeline keeps its compiled code. Every device has a **pipeline cache** keyed by everything a compiled pipeline depends on (layout and module serials never reused on the device, entry points, vertex layouts, fixed-function state; not the label); entries are dropped with their module or layout; every creation still returns its own handle. `compile_*_pipeline(desc, &Executor)` validates synchronously and compiles on the pragma.core executor's **blocking pool**; the caller installs the result with `poll_*` (non-blocking, once per frame) or `wait_*` (outside pool work). The device is never touched from another thread; a layout destroyed during compilation makes the result `StaleHandle` | The same explicit-lifetime model as #9 extended to the objects that reference others, so no destroy can leave a dangling reference for command recording (M3). A cache keyed by the validated descriptor avoids recompiling identical pipelines, which engines request repeatedly per material. Driver compilation can take milliseconds to seconds; the blocking pool is pragma.core's place for such work (pragma.core async), and polling keeps the frame thread in control of when results appear | 2026-11-09 |
| 15 | Command recording and submission | A `CommandEncoder` records **plain data**: commands that name resources by handle, with no device access, no lock and no fallible call; passes are scoped borrows of the encoder (`RenderPass`, `ComputePass`). `Device::submit` validates every command of every buffer against the live tables (handles, usages, alignments and ranges, attachments, pipeline and bind group compatibility, dynamic offsets, draw ranges, late `min_binding_size`, WebGPU usage scopes) and resolves handles before the backend sees anything; a broken rule rejects the whole submission with `RhiError::InvalidCommand` (command buffer label + command + reason). Recording on the frame graph goes through `CommandGraph`: each recording task fills one encoder labeled with the task name, declares access by type like any pragma.core task, and the buffers come back in the graph's topological order; a failed recording keeps its typed `RhiError`, the first in that order wins. Resources referenced by recorded but unsubmitted commands are not pinned: a destroyed one is `StaleHandle` at submission. wgpu encodes the validated commands on the submitting thread | Parallel recording needs encoders that are `Send`, independent of the single-owner device (#14) and cheap; plain data gives that and keeps the device lock-free. Validating at submission in our front end, instead of letting wgpu reject commands, makes the null backend reject exactly what wgpu rejects (as #13 does for shaders) and turns wgpu's opaque validation strings into typed errors that name the task. Rejecting a submission as a whole means no half-executed frame. Topological order is deterministic on any number of workers, which golden images and replays need. Encoding wgpu commands per submission is single-threaded; if M5's benchmarks show it matters, batches can be encoded in parallel (wgpu encoders are `Send`) without changing the API | 2026-11-09 |
| 16 | Null backend memory | The null backend keeps the bytes of buffers and textures, allocated lazily on first write (reads of unwritten memory are zero), one sample per texel, laid out linearly per layer and mip. It executes queue writes, buffer clears, every copy, attachment clears (with WebGPU's conversion: unorm round-to-nearest, sRGB encoding of color channels, f16 round-to-nearest-even), resolves (a copy: every null sample holds the same value) and `StoreOp::Discard` (zeros). Draws and dispatches are validated and have no effect. Readback (`read_buffer`, `read_texture`) is blocking before frames in flight (M4) | Readback tests and the vertical slice must run on CI runners without a GPU; transfers are fully specified, so the null backend can reproduce them exactly — and does: the M3 tests compare the bytes with Vulkan, D3D12 and WARP. Shaders would need an interpreter, which is out of scope; deterministic no-op draws keep the null backend's output stable. Lazy allocation keeps large null resources (budgets up to GiBs in tests) free until used | 2026-11-09 |
